# 源 C：论文整理

## 铁律：先通读，再动笔

**先把全文读完、形成全局认识，再开始写**。不要边读边写——边读边写会把"局部细节"误当"核心洞见"，也会导致层级混乱。

## 读取流程

1. 用 `references/toolchain.md` 的 fitz 脚本把 PDF 抽成 UTF-8 全文文本，通读。
2. 图表中的公式/关键数字：正文文本层通常已含，优先用文本；纯公式/代码图再走 OCR。
3. 通读后，先在脑中（或简短列出）回答："痛点是什么？洞见是什么？方法是什么？关键结果？经验技巧？"再动笔。

## 组织架构：总—分

**总**（一段话）：这篇论文做了什么。

**分**（四块，按此顺序）：

1. **痛点 / 洞见 → 方法**：针对什么痛点、基于什么洞见，提出了什么方法。
   - ⚠️ 洞见必须**忠于论文本身**。区分清楚："论文继承自前人的框架/前提" vs "论文自己的核心洞见"。
   - 不得把"根据用户提问衍生的解释"写成论文洞见。若某解释是为帮助理解而加，标注清楚它是补充，而非原作主张。
2. **方法要点**：核心机制 + 关键公式。能画主流程就给总链路（`->` 链或伪代码）。
3. **效果**：**只提关键结果**，不堆全部表格。挑最有代表性的 1–3 个数字/结论（如精度损失、加速比、可跑的最大规模）。
4. **实现与实验经验技巧**：论文里那些对实际做量化/训练/工程很有用的经验性细节（校准集怎么选、超参怎么设、数值稳定怎么保证、什么场景失效等）。

## 层级纪律（源自用户反馈）

- 同级章节内容必须同层级。不要把"某个公式的解释"和"算法的整体步骤"并列成同级。
- 常识性前置概念（如基础定义）精简后放到**文末附录**，不要占据正文核心位置。
- 收尾的"常见误解"若零碎，就近融进正文一处一次，不要堆成长清单。
