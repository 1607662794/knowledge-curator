# 用户笔记风格（铁律 + 真实范例）

来自用户既有笔记与记忆 `笔记整理格式偏好`。整理拿不准时读这里对齐。

## 铁律

1. **开头「0. 一句话结论」**：先给整体心智模型/核心摘要，让读者一开始就知道这页在讲什么。
2. **紧接「1. 总链路」**：能画主流程处，用 `->` 箭头链或伪代码给出完整信息流骨架，建立全局视角。
3. **编号章节**：用 `0, 1, 2, 3...` 编号组织，逻辑层次清晰；同级不混层。
4. **保留完整代码路径**：不要截断成 `protocol.py:170`，保留全路径如 `vllm/vllm/entrypoints/openai/protocol.py:170`。
5. **保留上下文与 nuance**：像"SamplingParams 默认 output_kind 是 CUMULATIVE，但 OpenAI chat 路径会覆盖掉"这种关键细节不能丢。
6. **默认不加「常见误解 / 易错点」段**：用户明确表达过反感——"能融汇到笔记正文中的内容就不要单独罗列，全是阅读成本"。所以**默认把误解点就近融进正文对应句子**（如讲 `M` 的取值时顺带一句"所以'取大点更安全'是反的"）。只有两种情况可以单独立段：① 该笔记已有这种小节、要往里追加；② 误解点多且分散、正文实在放不下。**新写的笔记不要自己开这个段**。
7. **不要罗列常见文件/常见命令清单**：`ls` 出来的目录树、包里的文件列表、一眼能查到的命令表，都是低价值高成本。只留下"不查文档想不到"的那部分。
8. **表格列要完整**：不为简洁砍列，用户要完整信息。
9. **双链优先**：相关概念用 `[[笔记名#小节]]` 串联，宁可多链。
10. **不要压缩内容**：整理后的笔记要足够完整，读它就够、不必回看原文；但"完整"不等于"冗余"——去掉与理解无关的铺陈。
11. **frontmatter**：若原笔记有 Sub-item 等 frontmatter，保留。
12. **总链路与流程图/结构图画成 drawio 图，不要用文本画**：「1. 总链路」以及任何超过三五个节点、或有分支汇聚的图，一律用 `drawio-skill` 生成图文件（存本笔记同级 `images/` 目录），笔记里嵌入引用。文本 ASCII 图只保留给**三四个节点的线性单链**（`A -> B -> C`）。具体产出格式与流程见 `references/diagram.md`。
13. **去掉原文里的无用链接**：从知乎/博客/其他 AI 复制来的内容常带一堆站内跳转（如 `[主元](https://zhida.zhihu.com/search?...)`）、追踪参数、"点击查看"锚点，**全部删掉**。只保留有信息价值的外链：论文 arXiv 页、官方文档、源码仓库。
14. **知识点要抽象成通用知识，而非案例记录**：除非用户明确说"记录这个 case"，否则把一次具体排错/一次对话抽象成可复用的通用条目——写"什么机制导致什么现象"，不写"我那天遇到 X 然后执行 Y"。这条与核心原则直接相关，违反它等于把笔记变成日志。
15. **语言**：中文。

## 低阅读成本 = 最高优先级

用户最看重"快速可习得性"：以最低阅读成本完整承载知识点。完整（不丢 nuance）与精简（不冗余）二者要兼顾——丢信息和堆废话都是失败。

**用最小的代价换最大的收益**：一句话讲得清的不写一段，一段讲得清的不写一节，不配小标题的不硬造小标题。用户的原话是"知识点的完善补充应该以最小的代价获得最大的收益，简洁高效"。判据是**信息密度**而非篇幅：每句话都得带新信息，一旦出现"换个说法再说一遍""再给个典型案例""最后串一下链路"，就是在堆阅读成本。

对照一个真实的失败/修正例：用户只说"完善一下 `ps` 检索进程的细节"，第一版写了 81 行（三张语法对照表 + 一节"判断后台脚本是否还在跑" + 四种等价写法），被判定为"完全是垃圾、把笔记当垃圾场"；修正版 21 行，只留「三套语法不能互推」+「`a`/`x`/`u` 各管什么」+「为什么 `ps -a | grep` 查不到」+「`grep` 匹配自身」，信息一条没少。

## 真实范例（读 vault 内文件对齐手感）

- **论文类总-分结构**：`算法工程工作内容/※ 算法工程/压缩/smoothquant.md`、`GPTQ.md`
  （纲领 → 痛点/洞见 → 方法要点 → 效果关键结果 → 经验技巧 → 附录/常见误解）。
- **碎片知识点通用化**：`算法工程工作内容/计算机基础/操作系统/linux.md`
  （把一次问答抽象成通用条目，配最小示例，编号小节，双链串联）。
