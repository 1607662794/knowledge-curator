# 源 A/B：当前对话 / 本地聊天记录

A（当前对话）与 B（本地聊天记录文件）用**同一套**抽取形式。B 的唯一差异是先读文件。

## 触发信号

- **A 类**：用户通常说"把刚才聊的 X 整理进 XX 笔记""同步一下这个知识点"。
- **B 类**：用户给出一个本地「聊天记录」文件路径（来自帖子、其他 AI 交互记录等碎片）。

## 抽取规则

1. **第一优先级 = 用户问题中提到的知识点**。把它抽象为**通用知识格式**并凝练，而不是复述对话过程。
2. **独立问题独立成条**，不要牵扯上一轮对话的上下文——用户明确讨厌"明明是独立问题，非要扯之前的对话"。自己独立总结成一个自洽的主题。
3. **必要时辅以最小使用示例**（如某个典型类的用法、一小段调用代码），但不堆教程式细节。
4. **匹配目标笔记的写作密度**：融入既有小节，别另起风格突兀的大段。
5. **跳过 off-scope / case-specific 内容**：与该笔记主题无关、或只在那次对话场景成立的一次性细节，除非用户明确要求，否则不写。
6. **清掉原文的无用链接**：复制自知乎/博客的正文常带大量站内跳转（`[主元](https://zhida.zhihu.com/search?content_id=...)`）、追踪参数、"点击查看/展开"锚点，一律删。只保留论文 arXiv 页、官方文档、源码仓库这类有信息价值的外链。网页 URL 抓取可参考 `_vendor/obsidian-skills/defuddle/SKILL.md`。

## 源材料缺内容时怎么办

用户说"融汇聊天记录里的 X 知识点"，但**该文件里可能根本没有 X**（记错了是哪份文件、或 X 在别的记录里）。处理方式：

1. 先 grep 关键词确认，**用 Grep 工具复核一遍**（Bash 的空输出不可靠，可能是环境问题而非真无匹配）。
2. 确认没有 → **不要临时找一个相邻话题顶上去**（这正是"HTTP 状态码写成 pip 403 排错"那次失败的成因）。
3. 顺手扫一下同目录其他记录文件，找到了就说明"X 在 `20260727.txt` 而非你给的 `20260728.txt`，已按该文件整理"。
4. 都没有、或目标笔记已覆盖 → 该条**留空并在结尾显式说明**，不静默跳过、不拿别的内容充数。

## 他源核实（约束 d）

B 类里若是 GPT/Gemini 等其他模型的对话：**融入前必须核实正确性**。GPT 类回答常冗长且可能有错——发现错误要**纠正后再融入**，而非照搬。冗余的箭头图、重复示例要压成紧凑表格或要点。

## 去重（主链路第 2 步的落地）

融入前搜目标笔记，判断该知识点是否已存在（到"事实"粒度，不是关键词）。已覆盖则跳过或只补差异，并在结尾说明跳过了什么。

## 与 chat-to-notes-curator 的关系

本 skill 内化了 chat-to-notes-curator 的全部可复用原则（融入既有结构、匹配写作密度、跳过 off-scope）。用户在本 skill 建成后会删除 chat-to-notes-curator，因此**不要 import 或依赖它**。
