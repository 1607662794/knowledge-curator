# 源 D：代码仓库整理

## 架构描述法：按仓库规模三档自适应

**动笔前先声明本次选了哪一档及理由**（用户看重低阅读成本，别无脑上最重的框架）。

| 档位 | 适用 | 用什么 |
| --- | --- | --- |
| 小仓库 | 单一职责、模块不多 | 分层架构图（文字）+ 关键路径序列图 |
| 大仓库 | 多容器/多组件 | **C4 精简版**：Context → Container → Component 三级（省略最细的 Code 级） |
| 超大仓库纵向穿刺 | 用户针对某个点深入学习 | 分层架构图 + **该路径的关键序列图**，只穿刺这条线，不铺全景 |

> C4 四级本是 Context→Container→Component→Code；这里刻意省掉 Code 级，因为对个人 KB 而言逐类逐函数太细、阅读成本过高。用户明确会在学习中对不同点做纵向穿刺，届时优先第三档。

## 覆盖角度（按需取用，不必全上）

- **典型架构设计的抽象概念**：这个仓库示范了哪些可复用的设计范式（插件化、分层、事件驱动等）。
- **该仓库的架构设计**：模块怎么划分、各自职责。
- **数据链路（data flow）**：一条请求/数据从入口到出口怎么流动——这是最该画主链路的地方。
- **关键数据结构**：核心的类/结构体及其字段含义。
- **关键设计取舍与扩展点**：为什么这么设计、在哪扩展、有什么坑。

## 组织成笔记时

- 开头一句话结论：这个仓库是做什么的、用什么架构范式。
- 数据链路用 `->` 箭头链或序列图给主链路。
- 关键数据结构/设计用表格或短列表，保留**完整代码路径**（不截断成 `foo.py:170`，给全路径）。
- 双链串联到已有的相关概念笔记。
- 去重：仓库的目录结构、git 历史能自解释的内容不必抄进笔记，只记"非显而易见"的设计与取舍。
