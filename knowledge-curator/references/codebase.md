# 源 D：代码仓库整理

先读 `style.md`；在动笔前简短说明选取的架构范围及理由，不把仓库全貌当作每次任务的默认范围。

## 按规模和问题选择表达

| 场景 | 表达方式 |
| --- | --- |
| 小仓库、职责单一 | 简要职责说明；关系复杂时补分层图或关键路径序列图 |
| 多组件 / 多容器 | 按需要采用 C4 的 Context → Container → Component，避免为层级完整而展开无关部分 |
| 大仓库中的具体问题 | 只梳理该路径的必要分层与关键调用 / 数据流，不铺全景 |

需要图时统一按 `diagram.md` 生成 draw.io 图；简单三四步线性关系可用一句话或箭头链，多分支关系不画成 ASCII 图。

## 按需覆盖

- 关键模块职责、实际数据流与核心数据结构。
- 可复用设计范式、实现取舍、扩展点及其限制。
- 有证据支持的行为与性能条件，不将命名猜测或注释意图当成已实现事实。

## 写入笔记

开头给主题结论，围绕用户要求说明机制；表格或短列表组织关键结构。同一术语、代码名与数学符号对应清楚；涉及算法变量、复杂度或不变量时明确其定义、维度和成立条件。

保留可定位的完整仓库相对路径及必要行号 / 版本，例如 `vllm/vllm/entrypoints/openai/protocol.py:170`。代码版本变化可能使行号失效，关键引用需核实。关联到必要的既有概念双链，不抄目录清单或整段源码冒充机制解释。

完成后按 `testing.md` 的通用项验收，有自绘图再执行绘图专项。
